# ロードマップ（`docs/ROADMAP.md`）

このドキュメントは、**InstaDirectOnly が今後どの方向に伸ばしていくか / 逆に何をスコープ外とするか** の一次リファレンスです。個別の Issue / PR で散在しがちなスコープ判断の根拠を集約し、新規コントリビュータや利用者が後から追えるようにすることを目的としています。

各項目は「必ずやる」という約束ではなく、**現時点でメンテナが妥当と考えている方向性のスナップショット** です。優先度や採用可否は、実装コスト・URL ポリシーとの整合性・Instagram 側の仕様変化に応じて随時見直します。

- 実装済みの機能一覧 → [`README.md`](../README.md) の「特徴」節
- 変更履歴 → [`CHANGELOG.md`](../CHANGELOG.md)
- リリース手順 → [`docs/RELEASE.md`](./RELEASE.md)
- アーキテクチャ全体像 → [`docs/ARCHITECTURE.md`](./ARCHITECTURE.md)

## 設計原則（Principles）

以下は、ロードマップ上の全ての判断において前提となる **変えない方針** です。新しい機能追加や外部連携の是非は、まずこの原則との整合性で評価されます。

1. **独自バックエンドを持たない。** 認証情報・メッセージ・添付ファイルなど、Instagram のユーザデータを本アプリ独自のサーバやサードパーティサービス経由で扱わない。認証は Apple 標準の WebKit データストアに委譲する（[`README.md`](../README.md) の「プライバシー」節を参照）。
2. **Instagram の DM 機能だけに集中する。** フィード・リール・発見タブ・ショッピングなどの導線は URL allowlist と CSS 注入で明示的に隠す。DM 以外の機能を「便利だから」という理由で追加しない。
3. **URL allowlist は deny-by-default。** 新しいホスト・パス・スキームは、明確なユースケース（DM 完結に必要か、ログイン導線か等）が示された上で個別に追加する。部分一致（`host.contains(...)`）は使わない（詳細は [`README.md`](../README.md) の「URL ポリシー」節）。
4. **メンテナンス性を優先する。** Instagram モバイル Web 版の DOM 構造・エラーコード・SPA 遷移挙動に依存する箇所は、変更の影響範囲が読みやすい形で 1 箇所に集約する（例: `mobileSafariUserAgent` / `hideUnwantedUICSS` / `isIgnorableNavigationError`）。
5. **UI は薄いラッパである。** 本アプリは `WKWebView` のラッパであることを隠さず、ネイティブ UI で Instagram のクライアントを再実装しない。

## 短期（Now）

現状すでに継続的に取り組んでいる、あるいは近い将来の PR で扱う予定のテーマ。

- **ドキュメント整備の継続。** [`docs/`](./README.md) 配下のインデックス（[`docs/README.md`](./README.md)）を軸に、アーキテクチャ・クラッシュ復帰・URL ポリシー・エラーハンドリングなどの一次情報を README から切り出して集約する動きを続ける。
- **URL ポリシーの回帰テスト拡充。** `InstaDirectOnlyTests/InstagramWebViewURLPolicyTests.swift` に、新たに追加された allowlist ルール・エラーメッセージマッピングに対応するケースを都度追加する（[`docs/TESTING.md`](./TESTING.md) 参照）。
- **CI の安定化。** `actionlint` / `link-check` / `typos` / `stale` などの Actions ワークフローについて、失敗時の切り分け手順を [`docs/CI.md`](./CI.md) にまとめ、新規ワークフロー追加時のガイドを維持する。
- **エラーメッセージの日本語化維持。** `InstagramWebView.userFriendlyErrorMessage(for:)` のマッピング表を新しい `NSURLErrorDomain` コードが顕在化するたびに更新し、README の対応表と一緒に回帰テストを追加する。

## 中期（Next）

現時点ではまだ Issue 化されていないが、原則との整合性があり、着手が視野に入っている項目。

- **iPad レイアウトの最適化。** `WKWebView` が iPad 上で提示する UI（モバイル Safari UA を送っていても iPad では余白が広くなる等）に対して、必要最小限の SwiftUI 側レイアウト調整を検討する。
- **アクセシビリティ改善。** VoiceOver ラベル・Dynamic Type・カラーコントラストなど、SwiftUI 側のオーバーレイ・進捗バー・エラー表示について再点検する。WebView 内部（Instagram モバイル Web 版）のアクセシビリティは Instagram 側の責務なので範囲外。
- **ローカライズ。** 現状のユーザ向けメッセージ・エラー文言は日本語ハードコード。英語ロケール（および将来的な他言語）への `Localizable.strings` ベースの分離を検討する。
- **リリースフローの自動化。** [`docs/RELEASE.md`](./RELEASE.md) の手順のうち、`MARKETING_VERSION` / `CURRENT_PROJECT_VERSION` の bump や `CHANGELOG.md` の `[Unreleased]` 節書き換えなど、機械的な部分をスクリプト化するかを検討する（Xcode プロジェクトファイルの安全な編集方法とセットで評価）。

## 長期（Later）

現時点ではスコープに含めるか未確定だが、要望として繰り返し出やすい / 一定の需要が見込まれる項目。**着手時期・採用可否ともに未定** です。

- **macOS Catalyst 対応。** Mac 上で本アプリを Catalyst として動かす選択肢。ただし macOS には Safari / ブラウザ拡張という代替手段が既にあり、独自クライアントを維持するコストに見合うかは要検討。
- **プッシュ通知。** 現状は独自バックエンドを持たない方針のため、Instagram 側のプッシュ通知 API を独自に利用する導線は取れない。APNs をアプリ側で受けるにしても、Instagram のログイン済みセッションから通知チャネルを確立する経路は現時点で存在しない。
- **Threads / Messenger 対応。** Meta の他 DM サービスに対して、同じ「DM だけを表示するラッパ」アプローチが成立するかは、各サービスの Web 版の作りや利用規約に依存する。**本リポジトリで一緒に扱うか、別リポジトリに分離するか** も含めて未定。
- **DM 履歴のローカルバックアップ。** 独自バックエンドを持たない原則を保ったまま、`WKWebView` 経由で取得できる範囲での UI 補助（例: 添付画像のダウンロードボタン）を検討する余地はあるが、Instagram の利用規約との整合性を優先して評価する。

## スコープ外（Out of scope）

以下の項目は、**現時点で明示的にスコープ外** としています。同種の要望が Issue に上がった場合は、このセクションを根拠にクローズします（原則そのものが変わらない限り、再検討はしません）。

- **独自バックエンド・サードパーティ解析サービスの導入。**
  原則 1（独自バックエンドを持たない）に反するため。ユーザデータを本アプリのサーバ経由で扱うと、プライバシー保証と URL ポリシーの deny-by-default 思想が崩れる。
- **Instagram の DM 以外の機能を UI 上で追加すること。**
  原則 2（DM だけに集中する）に反するため。フィード閲覧・投稿作成・ストーリー再生などは、既に Instagram 公式アプリ / モバイル Web 版が提供している。
- **ネイティブ UI で Instagram DM を再実装すること。**
  原則 5（薄いラッパ）に反するため。ネイティブ実装は Instagram の内部 API に依存することになり、規約・互換性・メンテナンスコストのいずれの観点でも本アプリのスコープを超える。
- **`javascript:` / `data:` / `file:` / `tel:` / `mailto:` などの追加スキーム許可。**
  原則 3（deny-by-default）に反するため。DM 完結に必須と説明できない限り追加しない。
- **URL allowlist の部分一致 (`host.contains(...)` / `path.hasPrefix("/direct")`) への緩和。**
  同じく原則 3 に反する。`evil-instagram.com.attacker.example` のような偽装ホストや `/directfake` のような prefix 取りこぼしを防ぐため、完全一致もしくは明示的なサフィックス判定（`.instagram.com`）を維持する。
- **Instagram 認証情報の自動入力・パスワードマネージャ連携の独自実装。**
  Apple 標準の AutoFill / iCloud キーチェーン導線は WebKit が既に提供している。それを超える独自実装は、独自バックエンド・独自パスワード保管どちらの方向でも原則 1 に反する。

## このドキュメントの更新方針

- **原則 (Principles) セクションは、変更する場合に必ず PR の説明で理由を明記する。** ロードマップ全体の判断根拠なので、静かに書き換えない。
- **Now / Next / Later は流動的なスナップショット** として扱う。PR や Issue の議論の結果、優先度が動いた場合はためらわずに書き換える。
- **Out of scope は「なぜ入らないか」の理由付きで書く。** 単に「対応しません」と書くと同じ要望が繰り返し提起されるため、判断の根拠（どの原則に反するか）を必ずリンクする。
- 大きな方針変更（例: 新しいプラットフォーム対応の正式着手）は、[`CHANGELOG.md`](../CHANGELOG.md) の該当バージョン節にも記録する。
